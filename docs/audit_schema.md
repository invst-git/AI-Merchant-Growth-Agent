# Audit Record Schema — Draft (Phase 0)

Every transaction the system touches should be reconstructable end to end
from one record. This is the field contract; the actual storage backend
(SQLite vs. append-only JSON lines vs. something else) is a Phase 6
decision, not a Phase 0 one — this doc only fixes what fields exist.

## intent
- `request_id` — unique id for this buyer interaction
- `timestamp`
- `customer_id` — simulated/demo customer identifier
- `raw_query` — the buyer agent's natural-language request, verbatim
- `parsed_intent` — the structured interpretation of that request (product
  category, constraints such as a price ceiling, etc.)

## decision
- `decision_id`
- `candidate_actions` — every action the engine scored for this basket,
  each with: action type (upsell / cross_sell / no_action), SKU (if
  applicable), the rule/lift that surfaced it, `P(accept)`,
  `incremental_basket_value`, `margin_proxy` used, `expected_downside`,
  and the resulting `expected_value`
- `chosen_action` — which candidate won, including the no_action case
- `reason_text` — a plain-English sentence generated from the winning
  candidate's numbers (this is what the dashboard shows a human)

## cart
- `cart_before` — line items, quantities, prices at the moment of intent
- `cart_after` — line items, quantities, prices after the chosen action
  was applied (identical to `cart_before` if the decision was no_action)
- `delta` — the difference, for convenience

## payment
- `razorpay_order_id`
- `razorpay_payment_id`
- `signature_verified` — boolean, set only after server-side HMAC-SHA256
  verification succeeds
- `status` — created / captured / failed
- `amount` — in paise
- `spend_cap_applied` — boolean, whether the bounded spend cap constrained
  this transaction
- `failure_reason` — populated only on a failed payment (e.g. the
  deliberate `failure@razorpay` test path)

## outcome
- `final_status` — completed / abandoned / failed
- `timestamp_closed`
- `experiment_run_id` — nullable; links this record to a Phase 5
  Control-vs-Agent experiment run, when the transaction was generated by
  the simulator rather than the live demo path

## Notes

- Every field above should be populated even when the outcome is
  no_action or a failed payment — those are not exceptions to log less
  carefully, they're the two things the Track's bar explicitly asks to
  see handled well.
- `reason_text` is generated, not hand-written, so it can never drift
  from the actual numbers the engine computed.
